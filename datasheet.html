一、Bootloader（产品基础设施）

原理（一句话）

Dual-image + 元数据契约 + 软复位换 SP/PC。 BL 用 Flash 头部 8 KB 装自己，剩余给 APP；通过 1 块 meta 和 1 块 boot flag 在两次复位之间传状态；CM0 没 VTOR，所以 BL 永久接管所有中断向量，靠 SRAM 软向量表转发给 APP。

必背配置（改一处错，板砖）

项必须值 / 公式改错的后果
BL 链接基址0x01000000复位向量取错 → HardFault
BL 大小预算≤ 8 KB (0x2000)越界擦 APP 区
APP 链接基址0x01002000（sector 对齐）与 BL 互撞
Meta sector0x01007800必须独占 1 个 512B sector
Boot flag sector0x01007C00同上
软向量表地址SRAM 0x20000000，96 BApp 的 RW 也用这片就崩
App scatter RAM0x20000060 起不让出前 96 B 就覆盖软向量
Flash 编程时序 SCU_Unlock → Flash_SCU24MHz_ClkCfg → Flash_Unlock → Flash_Main_WriteEease_Enable → 设 PEKEYR → 写地址 → 等 IFR 漏一步 IFR 永远不置位

5 个坑（都踩过）

  1. 24 MHz 下必须调 Flash_SCU24MHz_ClkCfg()，4 MHz 不用。混淆会让擦写永久 timeout。
  2. BL 不能给自己擦写 — BL 想升级只能 SWD。所以 BL 第一版必须测稳。
  3. error_blink_forever() 让 UART 静默。失败 1 次之后任何 ymodem 都不响应，必须 reset。生产用要保留串口 [BL] error code 3 提示而不是死循环。
  4. 3 秒窗口太短：reset 完到 PC 端工具就绪可能 >3s。生产建议 8s 或永久等（强制 boot flag）。
  5. HW CRC 范围是 inclusive：Flash_CRC(start, end) 算到 end 那一字节，别按 exclusive 算 size。

二、FreeRTOS（学习 / 复杂同步场景）

原理（一句话）

SysTick 触发 tick → 调度器决定要不要切换 → 置 PendSV pending → CM0 在中断退出尾部跑 PendSV → 保存当前任务 PSP / 加载下个任务 PSP。 每个任务有自己的栈（PSP），内核/中断共用 MSP，CONTROL[1] 控制 SP 选择。

必背配置（FreeRTOSConfig.h）

项4KB SRAM 推荐值不能这么改
configCPU_CLOCK_HZ24000000跟实际不符 → tick 错
configTICK_RATE_HZ1000高于 4kHz 浪费 CPU
configMAX_PRIORITIES3每加 1 个 readyList +12B SRAM
configMINIMAL_STACK_SIZE64 words (256 B)<40 idle task 都跑不起来
configSUPPORT_STATIC_ALLOCATION1必须
configSUPPORT_DYNAMIC_ALLOCATION0节省 heap_x.c (2-4 KB)
configTOTAL_HEAP_SIZE0不用 heap
configUSE_PORT_OPTIMISED_TASK_SELECTION0CM0 没 CLZ 指令，开了崩
configUSE_MUTEXES/TIMERS/EVENT_GROUPS/...全 0每开一个 +几百 B Flash
configCHECK_FOR_STACK_OVERFLOW0（性能）或 2（debug）2 比 1 准

接 TX32F01 startup 的关键宏（3 行救命）

#define vPortSVCHandler        SVC_Handler
#define xPortPendSVHandler     PendSV_Handler
#define xPortSysTickHandler    SysTick_Handler

FreeRTOS 默认函数名是 xPortXxxHandler，但 TX32F01 startup 向量表填的是 CMSIS 标准名。这 3 行让 port.c 编译出的强符号自动覆盖 startup 的 [WEAK] 符号。 没这 3 行链接器找不到 PendSV，调度器永远不切换。

5 个坑

  1. 静态分配必须实现 vApplicationGetIdleTaskMemory()，否则链接报错。
  2. 任务不能 return — 返回后会跳到 prvTaskExitError 无限循环。要么 vTaskDelete(NULL)，要么 for(;;)。
  3. CM0 临界区 = 全关中断（PRIMASK），不像 M3/M4 能 BASEPRI 屏蔽部分。临界区里别做长操作。
  4. xQueueSendFromISR 这类 ISR 函数才能在 ISR 调，普通 xQueueSend 在 ISR 调会断言失败。
  5. 要跑在 BL 之上：PendSV/SVC/SysTick 三个 handler 必须 通过 app_softvec_register_sys() 注册，FreeRTOSConfig.h 那 3 行 #define 不能用了（因为 BL 占了那 3 个符号）。每次任务切换多 ~250 ns 跳板开销，可接受。

三、协作式调度器（量产首选）

原理（一句话）

主循环遍历任务表，到点的就调一次然后返回，没人欠债时进 WFI 睡到下一个中断。 所有任务共用同一个栈（主栈），没有上下文切换、没有 PendSV、没有 SVC。

必背配置（coop_sched.h + main.c）

项推荐错的话
时间基SysTick @ 1 ms太快浪费 CPU，太慢 task 响应迟
任务表静态 coop_task_t s_tasks[]别动态分配，破坏确定性
next_run = now + period 不要用 += period 也别用 now + period 漂移版 漂移版长期看周期不准；+= period 在系统被打断后会"风暴执行"
任务函数原型void f(void) 无参加参就要全局变量传，反而乱
任务内禁止delay_ms()、while(uart_busy)、vTaskDelay()卡死所有其他 task
跑在 BL 之上的 SysTickapp_softvec_register_systick(coop_tick)BL 跳板找不到 ISR → tick 不走

1 个范式 + 5 个坑

范式：长操作必须 写成状态机。例： 原来 LED on; delay 50; off; delay 50; on; delay 800; → 拆成 6 个 50 ms 的状态步进。

  1. Task 必须 < 1 个 tick 周期内跑完，否则下次该跑的 task 被延后。50 ms tick + 60 字节 UART 打印（5 ms @115200）= OK；500 字节就危险。
  2. uart_putc polling 是阻塞的，但单字节只 87 μs，可接受。要快用 DMA + 状态机。
  3. 共享变量加 volatile（task ↔ ISR），但 CM0 上 32-bit 对齐字读写本身原子，不需要关中断。32-bit 以上（如 64-bit 计数）必须临界区。
  4. WFI 之前别关中断 — __disable_irq + __WFI + __enable_irq 模式会让 ISR 在 __enable_irq 之后才跑，导致状态变量已过期。直接 __WFI() 即可（pending IRQ 立即唤醒）。
  5. CPU load 测量很易出 bug（我们就踩过）。简单可靠的做法：数 1 秒内 WFI 进入次数，作为粗略 idle 指标。要精确就外加一个不停止的 timer 测 idle 总时长。

四、跨三者的共通原则

1. CM0 没 VTOR 是一切复杂度的根源

所有"为啥这么写"几乎都能追溯到这一点：

  • BL 必须永久接管所有 IRQ → 跳板机制
  • APP 不能改向量表位置 → 必须经过软向量表
  • FreeRTOS 跑在 BL 上要额外注册 3 个系统异常

2. Flash 写错就变砖，4 个安全栏杆

栏杆实现
地址校验bflash_erase_app_range() 拒绝写 BL 区
写前必擦永远 erase → program，flash 只能 1→0
写后必校验HW CRC + meta magic + size 范围
升级失败可回滚meta 校验不过自动留 BL，不跳坏 APP

3. SRAM 4KB 的余量管理（最稀缺资源）

0x20000000 ┌──────────────────┐
           │ 软向量表    96 B │ ← BL 用，APP 不能动
0x20000060 ├──────────────────┤
           │ BL 或 APP 的 RW  │
           │  ZI  /  stack    │ ← 谁占了多少全靠 .map 文件看
0x20001000 └──────────────────┘

BL:        ZI 1.6 KB（含 1 KB YMODEM 包缓冲）
APP_RTOS:  ZI 1.6 KB（4 个 256 B 任务栈 + 内核数据）
APP_COOP:  ZI 0.6 KB（共享一个 ~500 B 主栈）

新增功能前先看 .map，对 ZI 心里有数。

4. 调试三板斧

  1. UART print — 第一手现场，任何状态都能看
  2. JLink halt + regs + mem32 — 看 PC/SP/向量表，PC 范围立判正常/跑飞
  3. .map 文件 — 算精确的 Flash/SRAM 占用，对比预算

5. 何时选谁

SRAM < 4KB  且需要复杂同步     → 换芯片（不要硬上 RTOS）
SRAM < 4KB  业务不复杂          → 协作式调度器 ★
SRAM 4-8KB  少量任务            → 协作式 或 极简 FreeRTOS
SRAM ≥ 16KB 多任务 / 实时性强   → FreeRTOS / RT-Thread / Zephyr
